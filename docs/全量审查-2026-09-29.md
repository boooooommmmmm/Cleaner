## P1：优先修复

### F01 — `.gitignore` 漏掉必需的 Backup 源码

**位置：** `.gitignore:266` 的 `Backup*/`。

`git check-ignore -v` 确认 `src/CleanSweep.Core/Backup/RegistryBackup.cs`、`RegistryPath.cs`、`RestorePointService.cs` 全部命中。当前仓库没有提交，这三个文件尚未被跟踪；正常 `git add .` 会遗漏它们。StartupManager、AppServices 和测试已经依赖这些类型，因此交付不完整的源码后会编译失败。

**建议：** 收窄忽略规则或明确豁免源码目录，并在暂存文件清单及独立干净检出中验证完整构建。此结论由忽略结果和类型依赖确认，本次没有替用户暂存文件或创建提交。

### F02 — 注册表备份自动淘汰可以删除备份目录外文件

**位置：** `src/CleanSweep.Core/Backup/RegistryBackup.cs:116`，尤其 `:126`；自动调用入口 `src/CleanSweep.App/App.xaml.cs:70`。

`PurgeOlderThan()` 从数据库取出 `file`，直接 `File.Delete(v.File)`，没有限制它属于 BackupDir，也没有验证实际位置或重解析点。独立测试插入一条过期记录，路径指向备份目录外的临时 `important.txt`，执行淘汰后该文件被删除。

正常启动默认保留最近 20 条；复现把 keepAtLeast 设为 0 以隔离危险分支。真实触发需要目标记录处于这 20 条之外且超过保留期。有数据库写权限的进程能构造这些条件，后续启动维护将以应用权限尝试删除目标文件。

**建议：** 用内部备份标识推导路径；在删除前强制校验目录边界、实际对象和重解析点，失败拒绝；不要仅依赖数据库放置位置。

### F03 — 已存在目录只核对所有者，仍接受 Everyone 可写权限

**位置：** `src/CleanSweep.Core/Safety/ProtectedDirectory.cs:30`、`:37`。

`EnsureTrusted()` 对已有目录只调用 `VerifyOwner()`，`RestrictAcl()` 仅用于新建目录。复现创建当前用户所有、允许 Everyone Modify 的目录，调用成功，宽松 ACE 原样保留。可信所有者并不代表其他用户不能写入。

这影响 ProgramData 数据目录与隔离根的信任前提。新目录还显式授予当前用户 SID FullControl，所以同账户的普通进程修改权限也需纳入威胁模型；本次没有把 UAC 视为已证明可突破的安全边界。

**建议：** 校验有效写权限及继承规则；对已有目录执行受控修复或拒绝使用，同时检查子目录和已有文件的权限。恢复元数据的真实性还需独立保证。

### F04 — 隔离区恢复仍信任可修改的 `original_path`

**位置：** `src/CleanSweep.Core/Cleaning/Quarantine.cs:171`。

目前验证了隔离来源路径，但恢复目标仍直接取自 SQLite。复现先正常隔离文件，仅修改该条记录的 original_path，保持隔离文件及 sidecar 不变，随后成功恢复到 TestEnv 中被 PathGuard 拒绝的 `Windows\System32\review.txt`。

这不依赖 Junction，也不是“正常恢复必须禁止所有受保护目录”的简单问题：原始目的地需要与可信的操作记录绑定。当前路径校验无法区分真正的原位置与篡改后的目标。已有目标通常改用 `.restored` 名称，因此本次证明的是定向写入，不是无条件覆盖任意已有系统文件。

**建议：** 保存受保护且可验证的原始路径与对象标识，恢复时校验映射真实性和模块授权范围；不能只比较两个同样可写的副本。

### F05 — 注册表备份范围检查依赖同一份可篡改索引

**位置：** `src/CleanSweep.Core/Backup/RegistryBackup.cs:83`。

`.reg` 段头与 `rec.KeyPath` 比较，可防止仅改文件时越界，但 KeyPath 来自数据库。复现正常备份测试键 Original，随后同时改备份文件和数据库 key_path，Restore 成功向另一个测试键 DifferentTarget 写入值。测试只触及专用 HKCU 键。

前提是同时能改备份文件和索引；在该条件下，“只允许写回当初备份的键”的保证失效。另有目录检查只做字符串前缀、读文件校验后由 reg.exe 再打开文件的问题，尚未进行竞态复现。

**建议：** 对备份内容、范围、身份和备份 ID 建立可信绑定，并保证导入的就是已验证的内容；修补目录权限应与输入验证一起实施。

### F06 — 重复文件的保留副本可以已经变成其他内容

**位置：** `src/CleanSweep.App/ViewModels/DuplicatesViewModel.cs:183`。

保留检查只要求文件存在且大小相同。复现先查出两个内容为 `original` 的副本，再把拟保留文件改成同长度的 `modified`；界面所用条件仍为真，真实 CleanEngine 成功隔离另一份。原内容在原目录已无副本，仅剩隔离区中的版本。

本次执行了 DuplicateFinder 和 CleanEngine，并复用了界面判定表达式，没有驱动确认对话框。隔离期内可恢复，过期淘汰后可能丢失原版本。检查还发生在确认对话框之前，存在用户停留期间过期的问题。

**建议：** 把“至少保留一份内容一致的副本”作为执行层条件，核对保留文件的身份、快照和哈希，并尽可能保持验证与移动期间的对象稳定。

## P2：正式发布前处理

### F07 — 整目录快照只比较总大小和最大修改时间

**位置：** `src/CleanSweep.Core/Cleaning/CleanEngine.cs:315`。

复现目录含较新文件 A 和较旧文件 B；修改 B 为同长度内容，mtime 仍早于 A。总大小和最大 mtime 均不变，整个目录照常被移走。文件数量、相对路径和逐文件快照没有参与判断。`Windows.old`、`$WinREAgent` 是当前已启用的目录规则，此能力并非只留给未来残留模块。

**建议：** 记录并比较逐文件清单；不能安全核对的目录改用逐文件处理或拒绝。当前只挡住了部分变化，不能宣称所有扫描后变化都会被拒绝。

### F08 — 延迟任务名称冲突会覆盖其他启动项的任务

**位置：** `src/CleanSweep.Core/Startup/StartupManager.cs:832`、`:833`、`:853`。

任务名只来自显示名称，使用 TaskCreateOrUpdate。同名 HKCU/HKLM 项、无效字符替换后的同名项或前 60 字符相同的项会共用一个任务。复现确认 `Product/A` 与 `Product\A`、两个相同前缀的长名称得到相同结果。代码随后覆盖任务并禁用当前原项，前一个原项也可能已禁用；失败回滚还会删除同名旧任务。

未创建真实计划任务；名称冲突已动态验证，覆盖与回滚行为由调用链确认。

**建议：** 用稳定 StartupItem 身份、用户 SID 和来源生成唯一 ID；仅更新确属该项的任务；回滚恢复旧定义或只删除本次新建任务。

### F09 — 自动注册表备份无法撤销首次禁用

**位置：** `src/CleanSweep.Core/Startup/StartupManager.cs:643` 附近；`src/CleanSweep.Core/Backup/RegistryBackup.cs:86`。

首次禁用时 StartupApproved 值可能原本不存在。导出只能记录已有内容，随后创建禁用值；reg import 是合并导入，不会删除这个新增值。专用测试键中实际执行 SetEnabled(false) 后还原备份，禁用值仍是 3。

设置页已提示“新增的值会保留”，所以不是没有提示的导入语义问题；问题是自动备份不能完整撤销产品自身的首次修改。删除启动项时 `RemoveApprovedValue()` 也未单独保存 Approved 状态，恢复 Run 值可能改变原来的禁用状态。

**建议：** 保存值原先是否存在、类型和数据，以操作级撤销恢复；新增值在撤销时删除，避免用整键合并导入代替精确回滚。

### F10 — 备份文件删除失败后仍移除数据库记录并计成功

**位置：** `src/CleanSweep.Core/Backup/RegistryBackup.cs:126`。

复现用不允许共享删除的句柄锁住备份文件。PurgeOlderThan 返回删除 1 条，文件仍存在，记录已经消失，用户不能从界面选择它恢复。隔离区已修复的同类问题在备份模块重新出现。

**建议：** 仅在确认删除完成后移除记录；失败保留记录和错误，允许重试；不要吞异常后报告成功。

### F11 — 签名缓存永久按路径复用

**位置：** `src/CleanSweep.Core/Startup/FileSignature.cs:38`。

复现复制系统 cmd.exe 到临时路径，验证为微软签名后，用无签名文本覆盖该文件。同进程再次 Inspect 原路径仍返回微软签名，而同内容换到新路径返回非微软。刷新启动项不能清除此静态缓存。

这会影响可信标识、隐藏微软项以及保留建议；没有证明程序因此自动执行恶意文件。

**建议：** 缓存绑定文件身份和变化信息，变更后重新验证；敏感决策使用当前对象的验证结果。

### F12 — 设置中的 `DuplicateRoots:null` 会阻断主界面初始化

**位置：** `src/CleanSweep.App/Services/AppSettings.cs:35`；`src/CleanSweep.App/ViewModels/DuplicatesViewModel.cs:97`；`src/CleanSweep.App/App.xaml.cs:41`。

合法 JSON 可以令非空声明的 DuplicateRoots 为 null；Load 不纠正，DuplicatesViewModel 构造时 Where 抛 ArgumentNullException。复现加载和同一 LINQ 调用，异常确认。ShellViewModel 在 window.Show 前构造且在 AppServices 初始化 try 之外，因此全局异常处理即使展示错误，也不会继续完成这次主窗口构造。

**建议：** 对反序列化设置进行完整归一化和范围校验，至少补齐 null 集合；设置持久化采用临时文件加原子替换，减少中断损坏。

### F13 — 文件组内不响应取消，系统命令无超时

**位置：** `src/CleanSweep.Core/Cleaning/CleanEngine.cs:151`、`:375` 附近。

页面现在已把取消令牌传到引擎，修复了旧绑定问题。但 CleanFileSet 不接收令牌，只在 ScanItem 之间检查。复现在首个 MoveIn 开始时请求取消，四个文件最终全部移入，单项批次仍正常返回。大型文件组会持续处理。系统命令 ReadToEnd/WaitForExit 也没有超时或取消处理。

**建议：** 在逐文件和目录遍历中检查取消；预动作前也检查。对不可安全中断的系统操作明确显示状态和取消边界，设置合理等待策略，不能简单强杀所有系统命令。

### F14 — 两条服务账户临时目录规则缺少 24 小时保护

**位置：** `rules/system.json:14`、`:15`。

LocalService、NetworkService 的 Temp 规则是 safe/always，未设置 minAgeDays。用真实规则和 TestEnv 新建临时文件，系统扫描立即选中且 DefaultSelected 为 true。NuGetScratch 与 dotnet 已修复，不代表所有 Temp 规则均满足 README 的 24 小时承诺。

**建议：** 对临时目录统一施加最小年龄并增加覆盖真实规则的测试。文件年龄和当前未锁定都不能独立保证业务不再使用，描述应避免绝对保证。

### F15 — 停止服务超时后，恢复句柄可能没有恢复任何服务

**位置：** `src/CleanSweep.Core/Cleaning/PreActionRunner.cs:55`、`:88`。

代码确认：Stop 等待 30 秒超时后返回恢复句柄；依赖项跳过、很快进入 finally。若此时仍为 StopPending，Dispose 只检查 Stopped，因此直接释放句柄。服务稍后真正停止时已经没有本次操作负责重启。未在真实服务上动态触发此时序。

**建议：** 保留停止请求和原状态，处理 StopPending 后续完成，设置有限等待/后台补偿并记录恢复失败。当前“超时仍返回句柄”只修复了部分路径。

### F16 — 跳过项仍从结果列表消失，重复文件页还读取执行后的选择状态

**位置：** `src/CleanSweep.App/ViewModels/CleanPageViewModel.cs:153`；`src/CleanSweep.App/ViewModels/DuplicatesViewModel.cs:225`。

两页都主要用 Failures 决定是否保留行；快照变化、白名单等 skip 不属于失败，行会被移除。重复文件页在 await 返回后遍历当前 IsSelected，XAML 复选框和批量选择命令没有统一按 IsBusy 禁用。用户在处理期间改变选择，可能让未处理文件消失或已处理文件留在列表。

此项由报告结构、ViewModel 与 XAML 静态核对确认，未执行 WPF 自动化。

**建议：** 引擎返回逐文件成功/失败/跳过结果，界面按本次固定请求及实际结果更新；处理期间冻结选择或隔离展示状态。

## 进一步验证事项

这些观察不计入以上 16 项已分级缺陷；不能据此宣称攻击已成功。

- **句柄移动仍有按绝对路径重试的分支。** `HandleMove.cs:50` 在错误 87/123 时丢弃目标目录句柄，重新使用路径；句柄还允许 Delete 共享。与 README“没有可被 Junction 抢占的窗口”的绝对表述不符，需要故障注入和并发替换测试。源快照核对与打开实际移动句柄也尚未绑定同一文件身份。
- **启动维护占用 UI 线程。** `App.xaml.cs:46` 通过 Dispatcher 执行同步 reconcile/purge；大隔离目录可能导致窗口长时间不响应。应移动到受控后台任务，并与用户清理协调。
- **共享数据并发。** Local 会话 Mutex 与全机 ProgramData 数据目录作用域不同，不能阻止不同会话并行访问。不同页面也可以启动后台操作。需要评估跨会话文件动作及 BeginBulk/EndBulk 生命周期并发，而不能只依赖 SQLite 串行写入。
- **裸可执行文件名。** CommandLine.Split 未解析系统搜索路径，Build 用 File.Exists(exe) 判断缺失；如 `rundll32.exe ...` 可能被标作缺失。需要用真实启动命令覆盖路径解析，再决定缺失文件的禁用建议。
- **扫描异常与资源释放。** SpaceAnalyzer 的枚举器没有显式 Dispose，且只在递归入口检查取消；大量平铺文件与深层目录下应验证取消响应和句柄占用。规则目录递归枚举本身的访问异常也未按单文件拒绝处理。
