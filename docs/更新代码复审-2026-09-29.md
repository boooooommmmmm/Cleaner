## P1：优先修复

### R01 — 文件粉碎未拒绝硬链接，会毁坏未选择的文件

**位置：** [FileShredder.cs](../src/CleanSweep.Core/Privacy/FileShredder.cs)，第 45–73 行。

Shred 校验路径、重解析点和物理路径之后，直接打开文件覆写并 SetLength(0)。硬链接不是重解析点，这些检查无法判断同一文件对象是否还有其他名称。

**已复现：** 在 TestEnv 的受保护 ProgramFiles 目录创建原文件，在允许目录创建它的硬链接。只对允许目录中的链接执行 Shred；操作报告成功，原文件仍存在但长度变成 **0**。原路径本身被 Guard 拒绝，说明路径保护无法阻止通过另一个硬链接破坏其内容。

**影响：** 无需竞态；选择一个别名即可破坏用户没有选择的其他名称对应文件，而且不经过隔离区。

**建议：** 从用于覆写的同一个句柄读取文件标识与链接计数，拒绝多硬链接文件；把重解析点、物理位置、对象身份校验绑定到该句柄。不要把路径校验等同于文件身份校验。

**探针：** Repro_ShredHardLink_DestroysUnselectedProtectedFile。

### R02 — 备份淘汰仍可穿过备份根目录的 Junction 删除外部文件（旧 F02 部分修复）

**位置：** [RegistryBackup.cs](../src/CleanSweep.Core/Backup/RegistryBackup.cs)，第 275–330 行，重点第 292、314–316 行。

新代码用 BackupDir + 文件名约束数据库路径，并拒绝文件本身是重解析点，但没有验证 BackupDir 及其祖先。目录被换成 Junction 后，字符串仍在 BackupDir 下，最终删除的却是链接目标中的普通文件。

**已复现：** 构造 RegistryBackup 后，将空备份根替换成指向另一临时目录的 Junction；插入一条对应过期记录。PurgeOlderThan(1, 0) 返回 1，另一目录中的 victim.reg 被删除。

**前提：** 能替换备份目录或其祖先。默认自动淘汰还要求记录超过保留期且不在最新 20 条内；探针把 keepAtLeast 设为 0 以隔离危险分支。

**建议：** 删除时验证整条祖先链，并以固定、可信目录句柄限定删除对象；复用与隔离区同级的对象安全约束。构造时验证一次不足以覆盖后续目录替换。

**探针：** Repro_BackupPurge_FollowsBackupRootJunction。

### R03 — 同目录 sidecar 未形成独立信任依据，恢复范围仍可一起伪造（旧 F05 部分修复）

**位置：** [RegistryBackup.cs](../src/CleanSweep.Core/Backup/RegistryBackup.cs)，第 133–239 行。

索引、JSON sidecar、.reg 文件做一致性比较，可发现只修改部分副本的情况。但三者均为可写数据，SHA-256 没有密钥，也没有独立保护的原始范围/身份绑定。

**已复现：** 正常备份 Original 测试键后，将 .reg 的段头改为 DifferentTarget，同时更新 sidecar 和 SQLite 中的键路径及哈希。Restore 成功将值写入另一个测试键。

**前提与边界：** 需要同时写入数据库、备份文件和 sidecar。这证明的是“数据目录内容被修改后，恢复范围校验不能提供真实性保证”，不等于已经证明任意普通账户可以写入该目录，更不等于远程或跨账户提权。

**建议：** 明确受信任主体和威胁模型。若要求抵御同账户普通进程篡改，应由独立受保护的服务持有操作记录/密钥，并绑定备份 ID、范围、用户与内容；同时核验现存子目录和文件权限。若明确把数据目录写入者视为可信，应相应收窄安全承诺。

**探针：** Repro_BackupRestore_AllThreeWritableCopiesCanBeForged。

### R04 — 应用清单不可靠时，指纹残留仍被判为 Safe 并默认勾选

**位置：** [ResidueScanner.cs](../src/CleanSweep.Core/Residue/ResidueScanner.cs)，第 127–128、330–353 行；[AppFingerprints.cs](../src/CleanSweep.Core/Inventory/AppFingerprints.cs)，IsInstalled/Eval。

Scan 在 RegistryReliable=false 时记录“本次不把未找到卸载项当作已卸载证据”，但 ClassifyFingerprint 不执行这条限制。installedName / installedPublisher / packageFamily 查询不到就返回 false，随后风险变成 Safe。

**已复现：** 注入 RegistryCount=0 的新鲜清单，给一个刚写入 settings.json 的应用目录配置 installedName 指纹。该目录被扫描出来且 DefaultSelected=true，没有活跃度或可靠性降级。

**影响：** 清单读取失败、漏项或未覆盖某类安装方式时，仍在使用的软件配置可能被当作已卸载残留。相邻多用户分支也复用同一个当前用户清单；HKCU 与 PATH 检测仍取当前进程环境，不能可靠证明其他用户的软件不存在。这一多用户后果是静态分析，未做跨用户实测。

**建议：** 将检测改为“存在/不存在/未知”三态并记录各数据源完整性；错误、权限不足、用户清单不匹配时返回未知，不默认勾选。其他用户应使用按 SID 的清单，或仅显示需要人工确认的候选。

**探针：** Repro_Residue_UnreliableInventoryStillDefaultsFingerprintToSafe。

### R05 — 注册表清理没有执行前失效复核，会删除扫描后已经修复的条目

**位置：** [CleanEngine.cs](../src/CleanSweep.Core/Cleaning/CleanEngine.cs)，第 203–220 行；[RegistryOps.cs](../src/CleanSweep.Core/RegistryCleaning/RegistryOps.cs)，第 25–51 行。

注册表目标只携带键路径、视图和值名。清理时执行护栏检查、备份、删除，没有比较扫描时的值，也没有重新检查“目标程序不存在”这一删除依据。

**已复现：** 在专用 HKCU 测试区创建指向缺失 exe 的 App Paths 项，真实扫描器列出该项；随后创建 exe，模拟安装/修复完成；CleanEngine 仍删除该有效键并计为成功。

**影响：** 扫描和用户确认之间的软件更新、重装、服务修复会使结果过期。服务/计划任务删除也没有携带扫描定义及其失效依据，存在同类边界。

**建议：** 保存值/键或定义快照以及失效证据，执行前重新验证；变化或已经有效时跳过并提示重新扫描。备份并不能代替执行前的正确性判断。

**探针：** Repro_RegistryCleaning_DeletesRepairedEntryFromStaleScan。

### R06 — 可选提权服务使用 NullPreActionRunner，忽略必需的停止服务动作

**位置：** [ElevatedOperations.cs](../src/CleanSweep.Core/Elevation/ElevatedOperations.cs)，第 112 行；[system.json](../rules/system.json)，第 51–57 行。

服务侧创建 CleanEngine 时使用测试用 NullPreActionRunner。规则中的 preActions 被视为成功但没有执行。内置 windows.update-cache 包含 Safe 目标及 wuauserv/bits/DoSvc 停止要求，因此并非只有自定义恶意规则才会触发。

**已复现：** 隔离规则设置 stopService:ReviewNotAllowed。加载成功后，服务操作仍成功隔离了文件；真正的 ServicePreActionRunner 会拒绝不在允许列表中的服务。

**影响范围：** 可选服务的 RunRuleClean 路径；当前 App 直接使用真实 ServicePreActionRunner，这一发现不能套用为“GUI 一定没有停止服务”。服务路径可能在后台组件仍写入时移动其缓存。

**建议：** 使用真实预动作执行器并记录恢复结果；未支持该前置条件时应拒绝执行对应目标。

**探针：** Repro_ElevationRuleClean_IgnoresRequiredServicePreAction。

### R07 — 可选提权服务按隔离项 ID 操作时缺少所有者授权

**位置：** [ElevatedOperations.cs](../src/CleanSweep.Core/Elevation/ElevatedOperations.cs)，第 53–84 行。

PurgeQuarantineItem 只取 ItemId 后调用 Purge，未判断该对象属于哪个 SID；隔离记录没有按发起用户绑定授权。Restore 仅比较路径是否位于当前配置文件的兄弟目录，对没有解析到 Profile 的情况不拒绝，对分布在不同目录/卷的用户也不能准确判断。

**已复现：** 隔离临时 OtherUser/private.txt 后，用一个无关 SID 构造已认证客户端身份调用 Execute，仍成功永久删除该隔离项。

**前提与边界：** 探针验证的是服务操作分发层，不是绕过管道 ACL、进程路径或签名认证。实际风险要求客户端已通过这些前置认证；在未来允许非管理员使用服务时尤其重要。当前 GUI 尚未接入服务。

**建议：** 给隔离记录绑定 owner SID 和操作范围；先做对象级授权，再按 ID 取路径。用户配置文件解析失败时拒绝用户操作；全局维护操作单独授权。

**探针：** Repro_ElevationPurge_DoesNotCheckItemOwner。

### R08 — 空闲空间擦除会在 CreateNew 失败后删除原本存在的文件

**位置：** [FileShredder.cs](../src/CleanSweep.Core/Privacy/FileShredder.cs)，FreeSpaceWiper，第 134–180 行。

工作目录固定为卷根的 $CleanSweep.Wipe，文件名从 wipe-0000.bin 开始。代码在 CreateNew 成功之前把路径加入 files；若文件已存在，构造 FileStream 抛异常，finally 仍按该路径 File.Delete，把本次没有创建的文件删掉。

工作目录也没有拒绝 Junction，可能使写入落到未选择的目标位置。写入时所有 IOException 都被当作“磁盘已满”，其他 I/O 故障也可能被报告为成功。

**验证：** 静态确认异常与 finally 控制流。本轮没有在真实卷根创建该目录，也没有运行填满磁盘操作。

**建议：** 每次使用新建且权限受控的随机工作目录；拒绝目录及祖先重解析点；只登记并清理本次成功创建的对象。区分磁盘满与其他 I/O 错误，对清理失败返回明确结果。

## P2：正式发布前处理

### R09 — 注册表删除护栏允许删除受保护树的祖先

**位置：** [RegistryGuard.cs](../src/CleanSweep.Core/RegistryCleaning/RegistryGuard.cs)，第 119–140、162–170 行。

IsNeverTouch 仅判断目标是否等于受保护路径或位于其下，没有判断删除目标是否包含受保护子树。Microsoft 容器层数检查又没有统一 WOW6432Node 前缀。

**已复现：** CheckDeleteKey 对以下两条都返回 null（允许）：

- HKLM\Software\WOW6432Node\Microsoft\Windows\CurrentVersion
- HKCU\Software\Classes\Local Settings

它们包含声明永不触碰的子树。未真正删除这些键，也未证明默认扫描器会生成这两个目标；发现针对的是应独立成立的执行层护栏。

**建议：** 删除整树时同时拒绝受保护路径及其祖先，规范化 WOW64/视图表达，并限制具体允许删除的对象类型。

**探针：** Repro_RegistryGuard_AllowsDeletingAncestorsOfProtectedKeys，两个输入。

### R10 — TOKEN_PRIVILEGES 的托管布局不匹配，内存清理的特权启用失效

**位置：** [MemoryManager.cs](../src/CleanSweep.Core/Memory/MemoryManager.cs)，第 118–128、326–332 行。

原生结构包含 DWORD 与 LUID_AND_ATTRIBUTES；LUID 是两个 32 位字段。当前实现将 Luid 声明为 long，默认对齐产生了额外填充。

**已验证：** 当前构建的 Marshal 结果为 Luid 偏移 8、Attributes 偏移 16、总大小 24。按原生字段定义，单个权限项应分别为 4、12、16。AdjustTokenPrivileges 因而收到错误的 LUID/属性，不能正确启用请求的权限；界面可能误报“需要管理员权限”。

原生定义见微软文档：[TOKEN_PRIVILEGES](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-token_privileges)、[LUID_AND_ATTRIBUTES](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-luid_and_attributes)、[LUID](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-luid)。偏移结论来自这些字段定义与本轮 Marshal 实测的比较。

**建议：** 显式声明 uint LowPart / int HighPart 的 LUID 结构及原生嵌套结构，补充布局断言，再在隔离环境验证权限调整返回值。此次没有调用真实待机列表清理。

**探针：** Repro_TokenPrivileges_ManagedLayoutHasWrongLuidOffset。

### R11 — 系统命令一旦收到用户取消，就不再受超时上限保护

**位置：** [SystemCommand.cs](../src/CleanSweep.Core/Safety/SystemCommand.cs)，第 53–73 行。

linked token 先被用户取消时，catch 改用 WaitForExitAsync(CancellationToken.None) 等待；原 timeoutCts 后来超时不会再被观察。挂起的系统命令可能无限等待。此外，启动前没有检查已经取消的 token，取消后的后续调用仍可能启动命令。

**已复现：** 运行仅访问回环地址的 ping，超时 700ms，用户 token 在 100ms 取消；命令运行超过 2 秒，结果仍为 Success=true、TimedOut=false。

**建议：** 用户取消可以停止后续操作并等待当前命令，但这个等待仍应受独立超时控制；启动前检查取消。旧 CleanEngine.RunCommand 的循环保留了超时，本问题属于新增通用执行器。

**探针：** Repro_SystemCommand_UserCancellationDisablesTimeout。

### R12 — “针对某软件的残留扫描”仍包含其他软件的规则结果

**位置：** [AppServices.cs](../src/CleanSweep.App/Services/AppServices.cs)，第 165–171 行；[ResidueScanner.cs](../src/CleanSweep.Core/Residue/ResidueScanner.cs)，第 161–165 行；[RuleScanner.cs](../src/CleanSweep.Core/Rules/RuleScanner.cs)，第 36–69 行。

页面同时运行 RuleScanner.Residue 和启发式 ResidueScanner。OnlyAppName 只用于后者，规则扫描器没有该过滤条件，但页面仍声称本次是定向扫描。

**已复现：** OnlyAppName=RequestedApp 时，启发式结果为空，另一条 UnrelatedApp 的 uninstalled 规则仍返回结果，而且 Safe 项默认勾选。

**影响：** 用户从卸载页选择只扫描某软件，清理范围却包含其他软件。确认列表能显示这些项，但不符合入口承诺。

**建议：** 在两个扫描器共用的上下文或合并结果层按稳定应用身份统一过滤；完成事件后再清除过滤状态。

**探针：** Repro_TargetedResidueScan_RuleScannerIncludesUnrelatedApplication。

### R13 — 删除计划任务的 XML 备份没有恢复入口

**位置：** [RegistryOps.cs](../src/CleanSweep.Core/RegistryCleaning/RegistryOps.cs)，第 99–122 行；[SettingsViewModel.cs](../src/CleanSweep.App/ViewModels/SettingsViewModel.cs)，第 179–181、226–236 行；[ShellViewModel.cs](../src/CleanSweep.App/ViewModels/ShellViewModel.cs)，第 72 行。

DeleteScheduledTask 只写 tasks/*.xml 和 meta，然后删除任务；没有写入设置页使用的 registry_backups 索引，也没有对应的任务恢复实现。设置页只列出并导入 .reg 备份，而注册表清理页描述“每一项”都可以在设置中一键还原。

**影响：** 用户删除计划任务后，无法按产品提示恢复，只能自行找到 XML 并处理重新注册；任务身份、凭据等恢复要求也未形成完整流程。

**建议：** 实现独立任务备份索引与恢复流程，明确不能还原的凭据/主体限制；在此之前应修正页面承诺或暂停任务删除入口。

**验证：** 全仓库调用链与备份消费者检索，未删除真实任务。

### R14 — 多动作计划任务只要一个程序缺失，就被建议整项删除

**位置：** [RegistryCleanerScanner.cs](../src/CleanSweep.Core/RegistryCleaning/RegistryCleanerScanner.cs)，第 523–548 行。

遍历 Actions 时，只要一个 Exec 路径缺失就设置 missing；后续存在有效 Exec 或其他类型动作也不会取消该候选。执行时删除整个任务。

**影响：** 同一任务既有失效的旧动作又有仍承担工作的动作时，整项删除会丢失后者。当前风险为 Confirm，但提示没有解释其他动作仍可能有效。

**建议：** 保留全部动作及其检测结果；只在所有有效工作均已失效且可判定时给出整项删除建议，否则仅提示具体失效动作。

**验证：** 静态确认循环与 DeleteScheduledTask 调用链，未创建或删除真实任务。

### R15 — SMART 预警按枚举顺序分配给磁盘，可能标错故障盘

**位置：** [DiskHealth.cs](../src/CleanSweep.Core/Disk/DiskHealth.cs)，第 60、129–150 行。

物理磁盘列表按 Number 排序，而经典 SMART 查询只保留 PredictFailure 布尔列表，丢弃设备身份。只要数量相等，就按 predicts[i] 分配给 disks[i]，数量相等不能证明两个结果集的顺序一致。

**影响：** 多硬盘机器上，某盘的故障预警可能显示到另一盘，给用户错误的备份或更换依据。

**建议：** 保留 InstanceName/设备身份并建立可靠映射；不能匹配时显示未知，不按顺序猜测。

**验证：** 静态确认映射算法。未在多硬盘设备上制造 SMART 故障。

## 尚待专项验证的观察

以下不计入上面 15 项，以免把未完成验证的推断当作已复现缺陷：

- 启动维护改到后台后，Quarantine.Reconcile 与 UI/可选服务的 MoveIn 缺少统一操作互斥；MoveIn 先写 meta 再移动对象，Reconcile 会处理无对应对象的 meta。需要对这个窗口做故障注入，验证是否丢失恢复元数据。
- 全局 GUI 单实例锁不能阻止可选服务与 GUI 同时操作共享数据；多个页面的 IsBusy 也是局部状态。应验证清理、恢复、过期淘汰和卸载监听并行时的事务与对象一致性。
- 原目录指纹和重复文件哈希检查都在实际操作之前，未覆盖持续写入者的完整竞态；不能从正常回归通过推导“所有扫描后变化都能阻止”。
- UninstallWatcher 将新清单中消失的记录写成卸载历史，没有独立判断清单完整性；瞬时读取失败或安装器升级期间可能产生假历史，建议与 R04 的三态清单改造一起处理。
- 部分恢复按钮实现为写回一个默认状态：例如 IFEO 解除直接删除 Debugger、服务“恢复”设为自动，而非自动还原原值。已有备份提供人工恢复路径，但需要明确按钮语义和原状态保存策略。
