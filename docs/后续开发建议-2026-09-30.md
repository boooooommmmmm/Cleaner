# CleanSweep 后续开发建议

日期：2026-09-30。参考当前 README、产品设计 v0.16、审查修复状态，以及扫描、结果展示、操作日志、设置和空间分析相关代码。当前 HEAD 为 `92d90f0`。本文是开发规划分析，没有重新执行全量安全复审，也不把旧报告中的历史发现直接视为当前未修复问题。

## 1. 当前阶段判断

现有功能已经覆盖系统/应用缓存、残留、注册表、卸载、启动项、磁盘、驱动、隐私、隔离区、系统修复与更新等主要模块。近期还增加了规则目录通配、浏览器多配置覆盖，以及程序更新的验证、替换、回滚流程。

下一阶段最有价值的是：让用户理解每项操作、能够追踪和恢复结果，让发布版本在真实 Windows 权限环境中得到验证。新增功能优先围绕“空间为何增长、哪些数据可处理、处理后能否恢复”展开。

审查报告顶部已记录旧问题处理状态，其中 R03 是收窄威胁模型，并非建立了抵御同账户一致篡改的独立信任机制。若后续定位为多用户或企业工具，需要单独决定是否采用服务独占敏感记录的架构。

## 2. 优先级总览

这里的顺序是开发优先级，与安全报告中的 P1/P2 严重程度编号无关。工作量为相对估计，不是交付承诺。

| 顺序 | 开发内容 | 对用户/工程的价值 | 工作量 | 依赖 |
|---|---|---|---|---|
| A1 | Windows 虚拟机验收与持续集成 | 验证真实安装、权限、服务、恢复和更新 | 大 | 固定可重复的测试环境 |
| A2 | 扫描依据与影响详情 | 用户能判断为什么清、会失去什么 | 中 | 扩展结果模型和规则说明 |
| A3 | 按操作批次的恢复中心 | 从“找备份文件”变成“撤销上次操作” | 大 | 统一动作标识、备份关联和状态 |
| A4 | 安装/发布产物检查 | 减少包内容、版本、签名和升级路径不一致 | 中 | 现有发布与签名工具 |
| B1 | 磁盘空间历史与变化对比 | 回答“这周 C 盘为什么又满了” | 中 | 空间扫描快照 |
| B2 | 规则与指纹验证工具 | 扩大覆盖时控制误判，便于贡献规则 | 中至大 | 场景样本和期望结果 |
| B3 | 分阶段扫描与性能基准 | 更快得到首批结果，降低大目录扫描成本 | 中至大 | 性能测量、去重和取消机制 |
| B4 | 清理方案与设置导入导出 | 重复使用偏好，减少每次重新勾选 | 中 | 稳定规则 ID 和配置版本 |
| C1 | 定期扫描与空间预警 | 提前发现空间问题 | 中 | B1/B4、任务互斥、身份绑定 |
| C2 | 可访问性、多语言、诊断包 | 扩大可用人群，提高问题定位效率 | 中 | 文本资源化和隐私过滤 |

## 3. 近期最值得做的四项

### A1. 把真实权限验收做成可重复流程

README 仍明确列出真实提权环境、自更新真实下载安装、计划任务恢复等待验证内容。当前仓库没有 .github 工作流目录，可先增加自动构建/测试，再建立 Windows 虚拟机验收脚本。

第一批覆盖：

- 普通用户、管理员、UAC 输入另一管理员凭据、多个用户各自使用。
- 首次安装、重启后的服务连接、升级、更新取消、失败回滚和卸载。
- 文件被占用、磁盘空间不足、权限拒绝、数据损坏。
- 更新不同阶段异常退出，以及重新启动后的恢复行为。
- 文件、注册表值/键、计划任务的清理和恢复。
- 旧安装升级到新版本，隔离区与备份记录保持可读。

**首版验收：** 每个候选发布对应明确版本、安装产物哈希、测试环境和通过/失败记录；高风险流程失败时阻止发布。

现有回滚代码是基础，这项开发负责证明组合后的真实行为。异常中断与断电恢复不能仅靠正常抛异常的单元测试代替。

### A2. 给每个清理项增加“为什么”和“会怎样”

ScanItem 已有 Risk、Description、RuleId、快照和 MissingPath；ScanItemViewModel 主要展示名称、说明、路径、数量与权限。可以在现有列表上增加详情抽屉：

- 命中的规则及版本、适用应用或配置文件。
- 残留判定依据：发现卸载记录、程序目标缺失、清单可靠性等。
- 数据用途：缓存、日志、配置、存档，是否需要重新下载。
- 可恢复方式：隔离区、注册表备份、任务备份或不可恢复。
- 执行前置条件：需要关闭应用、停止特定服务、管理员权限。
- 跳过或失败原因及下一步，例如重新扫描、关闭占用程序、保留排除。

**首版验收：** 每个可勾选项目有清理依据、影响和恢复说明；无法确定用途的项目不凭“Safe”标签代替解释。失效证据结构化保存，界面展示与执行校验使用同一份信息。

这会同时改善用户体验和规则误判排查。

### A3. 按操作批次恢复

当前已有隔离区、注册表备份、计划任务恢复和操作日志，但入口和记录类型分散。可增加“恢复中心”：

- 按一次清理批次显示文件、注册表、计划任务及对应备份。
- 展示未开始、已处理、失败、待恢复、已恢复、备份过期等状态。
- 一次操作前先生成恢复预览，标明可恢复部分和不可恢复部分。
- 处理目标同名、内容已变化、应用已重新安装、备份不完整等冲突。
- 重复执行恢复不会误覆盖；中途退出后可继续核对未完成部分。

**实现建议：** 在 BatchRecord 基础上建立持久化 ActionId、备份/隔离对象关联、正向操作和恢复结果。先实现聚合查询与逐项恢复，再增加批次恢复。

**首版验收：** 用户可以从历史中的一次操作找到所有恢复材料；恢复前明确冲突，不把存在一个备份文件等同于保证完整恢复。

### A4. 发布前检查与升级通道

已有 publish、sign-data、release 脚本和 GitHub 更新来源，可继续增加：

- 发布包中程序版本、发布元数据、资产名称一致性检查。
- 三个数据集签名和安装清单检查。
- 在不接触私钥的构建任务中验证公开签名。
- 安装包与 ZIP 包的升级路径验收。
- 稳定版/预览版渠道，明确两者的数据和升级兼容策略。
- 规则最低引擎版本、规则语法版本，避免旧程序接收无法理解的新规则。

**首版验收：** 一条本地或 CI 命令完成发布前检查并生成报告；正式签名/发布仍使用受控的凭据流程。

## 4. 最有价值的功能扩展

### B1. 空间变化追踪

现有空间分析回答“现在谁占得多”，可扩展为：

- 保存用户选择的目录/卷的体积快照。
- 比较本次与上次扫描，列出新增、增长、减少最多的目录。
- 显示最近 7/30 天变化与应用分组。
- 标记隔离区占用、预计清理量、直接释放量。
- 用户只在已确认范围内进入现有清理流程。

现有清理结果已区分隔离体积和直接释放空间，应沿用这一语义。磁盘剩余空间变化还受其他程序写入影响，不能全部归因于 CleanSweep。

**最小版本：** 本地 SQLite 快照、两次扫描对比、增长目录前 20 名；不需要账号或云端上传。

### B2. 规则与指纹验证工具

当前文档列出 74 条规则和 69 条指纹，继续扩大时应同步提高验证能力：

- 输入规则与样例目录，只预览匹配，不执行删除。
- 每条规则有“应匹配、不得匹配、已安装、卸载后、多配置文件”样例。
- 检查宽泛通配、重叠目标、风险说明缺失、保护目录与白名单交叉。
- 比较新旧规则版本新增/减少的匹配项。
- 记录规则来源、兼容范围、最近验证版本。
- 对用户报告的误判生成脱敏样例，由维护者复核。

**首版验收：** 新规则附带正反样例；规则发布前可查看影响差异。先完善维护者工具，再考虑向普通用户开放规则编辑器。

### B3. 扫描性能和及时反馈

ScanScheduler 当前等待所有扫描器完成后合并结果；已有进度和取消能力。后续可以：

- 分批展示已完成的结果，并明确哪些模块仍在扫描。
- 将低成本的已知缓存扫描与全盘分析分开启动。
- 设置可调但受限的并发，避免大目录竞争 I/O。
- 保存扫描缓存，用于预览加速；删除时仍重新验证对象。
- 统一去重，避免多个规则重复计算相同文件体积。
- 建立固定小文件、大文件、深目录、无权限目录样本。

**首版验收：** 测量首批结果耗时、总耗时、取消响应和峰值内存。设计文档已有性能目标，先建立基线，再决定优化实现，不直接承诺加速比例。

### B4. 清理方案与偏好

在全局设置、白名单基础上增加：

- “日常清理”“开发缓存”“卸载后整理”等用户可保存方案。
- 按规则、应用、目录设置是否扫描和保留时间。
- “本次忽略”“忽略一段时间”“永久排除”分别处理。
- 设置/方案导出导入，标明版本和无效路径。
- 新规则加入后默认提示，避免旧方案自动扩大处理范围。

**首版验收：** 导出的方案不包含令牌、私钥、绝对用户隐私路径或隔离索引；本机专属路径若需要保留，应在导出时明确选择，并在导入机器重新确认。

### C1. 定期扫描与空间预警

先实现“扫描与提醒”，成熟后再评估无人值守清理：

- 每周扫描、空间低于用户阈值时提示。
- 避开已有清理任务；可设置电池供电、忙碌时跳过。
- 保存触发用户身份，不能因后台任务身份变化而改扫别人的目录。
- 对自动执行范围单独授权，仍遵守排除和执行前核对。
- 运行记录可见，失败能定位。

**首版验收：** 默认只生成报告；不自动删除注册表、服务、计划任务、个人文档或执行粉碎。

### C2. 可访问性与问题诊断

- 先完成键盘导航、高 DPI、高对比度、屏幕阅读器标签。
- 文本移入资源文件，再增加英文。
- 用户主动导出诊断包：程序/规则版本、错误码、受影响模块、脱敏路径。
- 导出前预览，不自动收集配置文件内容、凭据或浏览记录。

这些改进应与新页面一起完成，避免后期重复改造 UI。

## 5. 暂缓的方向

- **文件恢复、软件搬家、桌面整理：** 当前设计已经明确不做，继续保持范围。
- **更激进的注册表/驱动/系统组件删除：** 优先完善现有判定和恢复，不以删除数量作为扩展目标。
- **“一键内存加速”等无法稳定证明收益的操作：** 设计已排除 EmptyWorkingSet，不应重新引入相同方向。
- **账号、云同步、开放插件市场：** 当前核心使用流程尚不依赖这些能力，投入会带来额外的权限、隐私、兼容与维护成本。
- **只增加大量路径规则：** 与样例库、误判回归、规则影响预览一起推进。

## 6. 建议的三阶段计划

| 阶段 | 范围 | 完成标准 |
|---|---|---|
| 第一阶段：可验收 | A1/A4，加 A2 的详情预览 | 发布有可重复验证；用户能看懂每项操作 |
| 第二阶段：可追踪与恢复 | A3、B1、B2 | 一次操作能追踪与恢复；空间增长可解释；规则扩展有证据 |
| 第三阶段：高效日常使用 | B3/B4、C1/C2 | 扫描及时反馈；偏好可复用；提醒可控；界面可访问 |

如果只能选三个近期任务，建议选：**真实权限与升级验收、扫描依据/影响详情、空间变化追踪**。恢复中心同步先补数据模型，再逐步扩展界面和批次恢复。

## 7. 文档需要同步收敛

当前文档存在不同时间的状态混用：

- README 开头仍写“缺正式数据签名密钥”，后文已写正式 release 密钥。
- 设计文档待决问题仍列更新渠道，实际已采用 GitHub 来源。
- 审查报告正文保留历史未修复结论，顶部另有最新修复状态；应清楚标注历史基准，并链接对应验证结果。
- “实现完成”“单元测试通过”“真实环境验收”“已发布”应分别记录。

建议维护一张简短的能力状态表，避免后续开发把已实现功能重复列为缺口，也避免把已经提交代码当作已经完成产品验收。
