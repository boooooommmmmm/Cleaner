## 结论与验证范围

发现多处影响文件安全、隔离区恢复及配置可信度的问题。优先修复隔离区对数据库路径的直接信任、恢复和隔离区目录的重解析点检查、目录整体清理的保护缺口，以及文件系统和数据库状态不一致。

审查覆盖 Core 清理、隔离区、路径护栏、规则、扫描、数据库、白名单，以及相关 ViewModel。未修改产品代码。没有清理真实系统文件，没有执行 DISM 或停止真实服务，也没有进行跨账户提权攻击实验。

在现有 TestEnv 临时目录中增加并运行了 18 个审查用例，18 个均确认了对应的当前缺陷行为。这里的“通过”表示成功复现缺陷，不表示安全验证通过。复现源代码保存在 [审查复现用例-2026-09-28.cs.txt](审查复现用例-2026-09-28.cs.txt)，已移出正式测试项目。

本报告区分“已复现行为”“代码确认”和“尚未验证的攻击条件”。高优先级表示应尽快修复，不等同于已证明远程攻击或完整本地提权链。

## 1. 高：隔离区索引可指向隔离区外文件，启动维护直接删除

位置：`src/CleanSweep.Core/Cleaning/Quarantine.cs:131`、`src/CleanSweep.Core/Storage/AppPaths.cs:6`、`src/CleanSweep.App/App.xaml.cs:62`。

`Purge()` 直接使用数据库里的 `quarantine_path` 调用文件或目录删除，没有验证路径属于隔离区，也不调用 PathGuard。数据库存放于当前用户 LocalAppData，创建数据目录时没有建立供提权操作使用的独立信任边界。启动后会自动执行 `PurgeExpired()`。

复现：将一条隔离记录的路径改为测试环境中被 PathGuard 拒绝的 `Windows/System32/audit.txt`，并将过期时间设为过去。调用过期清理后，该文件被删除，原隔离文件仍存在。

影响：有能力修改该数据库的本地进程，可让后续提权运行的程序尝试删除隔离区以外、在其权限范围内的文件。该行为可能放大本地篡改的影响；本次未验证跨用户攻击和实际权限提升。

修复：把索引视为不可信输入；校验隔离路径的规范化结果、真实位置、所属卷、批次目录及重解析点；隔离区路径应由可信标识推导，而非任意数据库字符串。数据库和维护操作应放在明确的权限边界内。

## 2. 高：恢复路径和隔离区根目录接受 Junction

位置：`src/CleanSweep.Core/Cleaning/Quarantine.cs:58`、`:98`、`:239`。

`Restore()` 未校验原路径的父目录是否已被替换为 Junction。`MoveIn()` 对隔离区根目录也没有真实路径检查。`EnsureHiddenDirectory()` 仅在新建目录时设置 ACL；预先存在的目录不会重新校验权限，ACL 设置失败也被静默忽略。

已复现两个行为：

- 隔离文件后，把原父目录换成指向测试环境受保护目录的 Junction，恢复成功写入了被重定向的位置。
- 将测试隔离区根目录预设为 Junction，移入操作成功把文件写入链接目标。

影响取决于本地进程能否修改相关目录。可能造成恢复到错误位置、隔离内容落到未受预期权限保护的位置。本次没有复现跨账户攻击。

修复：验证源、目标及其祖先目录；拒绝重解析点；验证已有隔离区的所有者和 ACL。关键验证失败应停止操作。真实路径检查与实际移动之间也应避免竞态。

## 3. 高：整个目录清理可以绕过受保护子项，也会带走扫描后新增文件

位置：`src/CleanSweep.Core/Safety/PathGuard.cs:173`、`src/CleanSweep.Core/Rules/RuleScanner.cs:128`、`src/CleanSweep.Core/Cleaning/CleanEngine.cs:237`。

PathGuard 检查目标是否处于保护路径之下，但没有普遍拒绝包含保护路径的祖先目录。`CleanDirectory()` 只检查根目录，然后整体移动，不核对内部文件。

复现：自定义 directory 规则指向 `%UserProfile%\AppData`，加载和清理均成功，把测试环境中本应受保护的 `Roaming/Microsoft/Credentials/audit.txt` 一并移入隔离区。直接指向 `%AppData%\Microsoft` 的另一项探测被现有过宽目录检查拒绝，报告没有把它计为绕过。

另一个用例在目录扫描后加入新文件，整体清理仍把该文件移走。目录的扫描大小也因此不能准确代表实际移动量。

触发范围：自定义、被篡改或未来新增的 directory 规则。当前内置 directory 目标主要是尚未启用的卸载残留规则，因此不能据此声称默认 M1 扫描已经会整体清理 AppData。

修复：目录目标不得包含受保护对象；对内部条目应用同样的保护、白名单和快照检查。对无法保证一致性的目录，改用逐文件清理或拒绝整体移动。

## 4. 高：文件移动成功但数据库失败，会留下无法从界面恢复的文件

位置：`src/CleanSweep.Core/Cleaning/Quarantine.cs:58`、`src/CleanSweep.Core/Storage/CleanSweepDb.cs:117`。

`MoveIn()` 先移动文件，再写入索引。批量事务还会延迟索引提交。文件系统移动不随 SQLite 事务回滚。

已复现：

- 用数据库触发器模拟 INSERT 失败：原文件已经消失，隔离目录仍有文件，活动索引为空。
- 移入后丢弃未提交事务并重新打开数据库：索引消失，隔离文件仍在。该用例模拟未提交事务丢失，没有真的杀死进程。

影响：用户原位置找不到文件，隔离区列表也无法恢复；文件通常仍在磁盘上，但原路径映射可能丢失。启动时识别未完成批次不能自动重建这些索引。

修复：先持久化待移动记录，再执行移动并记录完成状态；启动时核对待处理记录和文件实际位置。增加写入失败补偿，明确区分恢复元数据和可批量延迟提交的普通日志。

## 5. 高：永久删除失败也会将记录标记为已清除

位置：`src/CleanSweep.Core/Cleaning/Quarantine.cs:131`，尤其 `finally` 中的 `Mark(id, "purged_at")`。

复现：以不允许删除共享的方式打开隔离文件，再调用 Purge。删除抛出 IOException，文件仍在磁盘上，但 ListActive 已不再返回它。

影响：文件无法从界面恢复或再次清理，占用空间也不再计入活动隔离区。整个目录部分删除失败时，残留条目同样可能失去索引。

修复：仅在确认删除完成或目标确实不存在时标记已清除；失败保留记录、保存错误并支持重试。不要把访问错误与目标不存在混为一谈。

## 6. 高：白名单未在实际清理前强制执行

位置：`src/CleanSweep.Core/Scanning/ScanScheduler.cs:40`、`src/CleanSweep.Core/Cleaning/CleanEngine.cs:44`、`src/CleanSweep.App/ViewModels/DuplicatesViewModel.cs:125`。

已复现：

- 白名单包含目录内部文件时，directory 目标仍被保留，整个目录移动带走该文件。
- 扫描完成后把目标加入白名单，再使用旧扫描结果清理，文件仍被移走。

原因是白名单主要作用于扫描阶段，清理引擎没有接收并核对最新白名单。重复文件页面直接调用 DuplicateFinder 和 CleanEngine，同样没有经过 ScanScheduler 的过滤，这一点为代码确认。

修复：所有破坏性操作在执行前统一检查最新排除项。目录整体操作需要检查它是否包含排除项。设置改变后应使旧扫描结果失效或重新过滤。

## 7. 中：系统命令白名单只约束可执行文件，不约束操作

位置：`src/CleanSweep.Core/Rules/RuleLoader.cs:164`、`src/CleanSweep.Core/Cleaning/CleanEngine.cs:295`。

白名单允许 dism.exe 和 cleanmgr.exe，但参数完全来自规则，直接传给进程。规则还可以将命令标为 safe。

复现仅验证加载：包含非清理用途 DISM 参数的规则被接受，风险等级仍为 Safe。没有执行系统命令。

影响依赖于规则可被修改。当前仅加载内置规则，若安装目录受到严格保护，攻击条件更受限制；若从用户可写目录运行，未签名规则的可信度更低。这里不是 shell 元字符注入：UseShellExecute 为 false。问题是授权范围过宽。

修复：规则引用固定操作 ID，由代码映射到经过审查的程序和参数；引擎强制不可恢复操作的最低风险等级，不能由 JSON 降级。

## 8. 中：合法 JSON 中的 null 可以令规则加载崩溃

位置：`src/CleanSweep.Core/Rules/RuleLoader.cs:87`、`:112`、`:129`。

`rules:[null]`、`category:null`、`targets:[null]` 均已复现 NullReferenceException，未进入正常的 Rejected 列表。非空 C# 属性声明不能阻止 JSON 输入 null。

影响：损坏的内置规则会使启动初始化失败或规则重载中断。

修复：验证集合元素和所有字符串的空值；限定 MinAgeDays 等数字范围；单条规则校验失败应转为清晰的拒绝原因。

## 9. 中：临时文件的年龄保护不一致

位置：`src/CleanSweep.Core/Rules/RuleScanner.cs:87`、`rules/dev.json:53`、`:109`。

复现：直接指向文件的规则即使带 `minAgeDays:30`，也会选中刚创建的文件，因为年龄过滤只用于目录枚举分支。

另一个使用真实内置规则的用例确认：刚创建的 NuGetScratch 文件会被默认勾选。NuGetScratch 和 dotnet 临时目录规则未设置年龄限制。它们可绕过系统临时目录规则中 24 小时的限制。

影响：正在运行的构建或安装可能需要暂时关闭的临时文件；文件没被操作系统锁定不等于业务上不再使用。本次没有运行真实构建来验证中断结果。

修复：文件目标与目录目标应用一致的年龄策略，对所有临时目录规则设定合适限制，必要时识别应用运行状态。

## 10. 中：停止服务失败后仍清理依赖该服务停止的文件

位置：`src/CleanSweep.Core/Cleaning/CleanEngine.cs:62`、`src/CleanSweep.Core/Cleaning/PreActionRunner.cs:49`。

复现：使用返回失败的模拟预动作，清理结果记录了失败，但目标文件仍被移入隔离区。没有停止真实 Windows 服务。

此外，停止服务后等待超时时，没有获得恢复句柄；服务可能稍后停止而不会由本次操作恢复。该分支为代码推断，未在真实服务上验证。

修复：明确规则的必要前置条件；条件失败时跳过依赖项目。可靠记录原始服务状态，并处理停止超时和恢复失败。

## 11. 中：显示的“已释放空间”包含仍占用磁盘的隔离文件

位置：`src/CleanSweep.Core/Cleaning/CleanEngine.cs:181`、`:271`、`src/CleanSweep.App/ViewModels/CleanPageViewModel.cs:145`。

同卷移动到隔离区不释放文件数据所占空间，但代码立即增加 FreedBytes。此为代码确认。

修复：分别记录移入隔离区字节数、永久删除字节数与实际可用空间变化。不要把移动量显示为磁盘空间释放量。

## 12. 依赖高危公告：SQLitePCLRaw.lib.e_sqlite3 2.1.11

项目解析出的 Microsoft.Data.Sqlite 为 10.0.0，传递依赖包含 SQLitePCLRaw.lib.e_sqlite3 2.1.11。构建报告 NU1903。

官方 GitHub 公告 GHSA-2m69-gcr7-jv3q / CVE-2025-6965 将该包 <=2.1.11 列入受影响范围。SQLite 3.50.2 的官方说明包含相关聚合表达式边界修复：

- [GitHub 安全公告](https://github.com/advisories/GHSA-2m69-gcr7-jv3q)
- [SQLite 3.50.2 发布说明](https://sqlite.org/releaselog/3_50_2.html)

本次确认的是依赖命中公告。没有验证该应用中可到达的漏洞触发链，也没有证据说明它提供远程 SQL 输入入口。应核对实际发布包内的 SQLite 原生版本并更新依赖组合，不能只隐藏警告或仅凭 NuGet 外层版本认定已修复。

## 13. 低：空间分析仍跟随作为扫描根的 Junction

位置：`src/CleanSweep.Core/Modules/SpaceAnalyzer.cs:89`。

空间分析跳过枚举到的子项重解析点，但没有在 Walk 开始时检查根目录。临时用例传入 Junction 根目录，成功统计了目标目录文件。

这是只读分析的边界问题，本次没有因此发生删除；但与“永不进入重解析点”的约定不一致。

修复：对扫描根和递归入口统一验证；显示跳过或拒绝原因。

## 其他代码观察与验证限制

- **清理前检查与移动之间仍存在时间窗口。** `PathGuard.ResolveFinalPath()` 打开并关闭句柄后，CleanEngine 才按路径调用 MoveIn。目录可能在两步之间改变。现有测试验证静态 Junction，不能证明消除了竞争条件。本次没有复现抢占竞态。需考虑基于句柄的操作及祖先目录稳定性。
- **失败项从界面消失。** CleanPageViewModel:135 和 DuplicatesViewModel:203 在执行后移除选中项，没有逐项区分成功、失败和跳过。用户需要重新扫描才能看到仍未处理的项目。
- **重复文件保留检查使用旧界面数据。** DuplicatesViewModel:170 仅判断是否全选，没有在执行时确认拟保留的副本仍存在且未变化。本次没有进行界面自动化复现。
- **清理取消不可用。** 页面忙碌时显示的取消按钮绑定 ScanCancelCommand，CleanAsync 使用 CancellationToken.None；命令执行也缺少超时。此为代码确认。
- **现有部分安全测试会静默略过。** Junction 创建失败后直接 return，会被测试运行器计为通过。本次新增 Junction 探测用 Assert.True 要求创建成功，并实际完成了测试。

## 修复顺序

1. 隔离区删除与恢复的路径约束、目录链接和权限边界。
2. 隔离区持久化状态机与删除失败处理。
3. 引擎层保护路径、白名单、目录快照约束。
4. 固定系统操作、服务前置条件、规则输入校验和年龄策略。
5. SQLite 依赖处理、统计显示和界面状态一致性。

`RiskLevel.cs` 枚举本身没有发现直接缺陷。安全等级只是分类，实际安全必须由不可绕过的引擎检查保证。
