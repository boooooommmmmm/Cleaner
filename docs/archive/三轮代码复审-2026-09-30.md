### W01 · 收尾工作区阻断 — 公钥已轮换，内置数据清单仍使用旧密钥

**位置：** [TrustedKeys.cs](../../src/CleanSweep.Core/Integrity/TrustedKeys.cs)、[rules/manifest.json](../../rules/manifest.json)、[fingerprints/manifest.json](../../fingerprints/manifest.json)、[popups/manifest.json](../../popups/manifest.json)。

09:42 的工作区只信任 release-2026-09，三个内置清单仍声明 dev-2026-09。实际运行正式测试，Bundled_data_sets_are_signed_with_a_trusted_key 失败，错误为“Rules: 签名密钥不受信任：dev-2026-09”。默认内置数据会被拒绝加载；如果本机另外已有有效受信任的数据集，实际选择结果另需按 DataSets 判断。

这是正在发生的密钥迁移状态，不应据此把旧开发密钥重新加入正式信任。应由持有新私钥的发布流程重新签署三个清单，随后重新运行验签测试并核对发布目录。审查没有读取新旧私钥或自行签署产品数据。

### N01 · P1 — 服务重新扫描扩大了用户确认的文件范围

**位置：** [ElevatedOperations.cs](../../src/CleanSweep.Core/Elevation/ElevatedOperations.cs)，第 104–134 行，特别是第 121 行；[ElevationContext.cs](../../src/CleanSweep.App/Services/ElevationContext.cs)，RunViaServiceAsync。

界面向服务只发送 RuleId 和 ItemIds。服务重新扫描并把新生成的 ScanItem 交给 CleanEngine，没有携带或绑定用户确认时的文件集合与身份快照。清理引擎即使比较了文件快照，比较的也是服务刚扫描的那份，无法约束到用户实际确认的范围。

**复现：** 扫描时目录内只有 A；保存选中条目的 ID 后创建 B；用该 ID 调用实际服务清理实现。A、B 都被移入隔离区，隔离记录为 2 条。B 不在用户扫描时的文件列表中。

**影响：** 扫描至执行之间新创建的数据也会被服务移动。服务侧重新校验规则签名、重新扫描，并不能替代用户确认快照。该问题适用于已启动服务上的规则清理路径；探针用临时目录模拟文件变化，没有驱动 WPF 或安装 SYSTEM 服务。

**修复方向：** 由服务生成并保存受限扫描结果/令牌，确认请求绑定同一份结果；执行时校验原对象身份及变化。新增或变化对象应跳过并要求重新扫描。不要为解决该问题直接接受客户端任意路径。

**探针：** `Repro_ServiceRescan_MovesFilesCreatedAfterUserScan`。

### N02 · P1（有前提）— 隔离区数据库分离时，同一个数字 ID 会操作另一文件

**位置：** [AppPaths.cs](../../src/CleanSweep.Core/Storage/AppPaths.cs)，第 20、46–61 行；[QuarantineViewModel.cs](../../src/CleanSweep.App/ViewModels/QuarantineViewModel.cs)，第 64–74 行；[ElevatedOperations.cs](../../src/CleanSweep.Core/Elevation/ElevatedOperations.cs)，第 66 行。

普通权限界面在不能写机器数据目录时使用用户数据目录；SYSTEM 服务使用机器目录。因此两端可能各有一份 cleansweep.db。界面本地恢复/删除遭遇特定权限异常时，回退请求只发送数字 ItemId。服务直接在自己的数据库按该 ID 查找，协议没有数据库身份或全局唯一对象身份。

**复现：** 创建两个独立索引，界面库的 A.Id=1，服务库的 B.Id=1，但路径不同。以当前同一用户 SID 把 A.Id 交给服务删除，返回成功，实际 B 被永久删除，A 仍在。此问题与 R07 的跨所有者授权不同：同一用户的两个数据库也能出错。

**触发前提：** 两端实际选择不同数据库，且界面操作进入服务回退。服务启动时的 ProtectedDirectory 校验/ACL 收紧也需要纳入这一分支的端到端验证；它不能被假定为始终保留安装用户的普通写权限。当前复现验证了双库 ID 冲突后的真实服务分发行为，没有模拟整个 SYSTEM 登录与 ACL 初始化过程。

**其他后果：** 分库时界面只列本地索引，无法看到服务隔离的新记录。直接扩大机器目录写权限不能替代可信数据和对象身份设计。

**修复方向：** 让服务持有权威索引并提供按用户授权的列表/操作 API；或使用全局唯一对象 ID，并绑定存储实例和所有者。必须拒绝来自另一索引的 ID。

**探针：** `Repro_SeparateIndexes_ForwardedNumericIdPurgesDifferentFile`。

### N03 · P1 — 服务长期缓存白名单，忽略界面后续添加的排除项

**位置：** [Program.cs](../../src/CleanSweep.Service/Program.cs)，第 133 行；[Whitelist.cs](../../src/CleanSweep.Core/Settings/Whitelist.cs)，构造函数与 Load；[ElevatedOperations.cs](../../src/CleanSweep.Core/Elevation/ElevatedOperations.cs)，规则扫描和引擎上下文。

服务启动时构造一次 Whitelist，此后使用同一个对象。界面修改的是自己进程中的对象和磁盘文件，没有通知服务重载。每次请求重新加载规则的实现没有覆盖白名单。

**复现：** 服务对象先读取空白名单；另一对象把测试文件加入同一份磁盘白名单，新建对象确认已被排除；随后服务仍成功隔离该文件。

**影响：** 用户扫描后添加排除项、再执行仍保留的选择时，服务可能忽略新策略。这里即使共享同一份 whitelist.json 也会发生，独立于 N02 的分库问题。

**修复方向：** 明确服务侧按用户保存的权威策略；通过 IPC 更新，或在请求时可靠重载并绑定版本。更新文件应原子替换；执行前复核最新排除策略。

**探针：** `Repro_ServiceUsesStaleWhitelist_AfterUiAddsPath`。

### N04 · P2 — 批量操作持有界面事务等待服务，服务删完文件后被索引写锁阻塞

**位置：** [QuarantineViewModel.cs](../../src/CleanSweep.App/ViewModels/QuarantineViewModel.cs)，第 109、144、177 行；[CleanSweepDb.cs](../../src/CleanSweep.Core/Storage/CleanSweepDb.cs)，第 115–124 行；[Quarantine.cs](../../src/CleanSweep.Core/Cleaning/Quarantine.cs)，第 239 行附近。

RunBulkAsync 用 BeginBulk 包围整个循环。操作需要服务回退时，界面保持 SQLite 写事务并等待服务。若双方共用数据库，服务永久删除隔离文件后，要更新索引时等待界面的事务释放；界面要等服务完成才会结束批量事务。

**复现：** 两个 CleanSweepDb 实例连接同一个临时数据库，界面实例开启批量事务，服务实例 Purge。隔离文件已经不存在，但服务任务仍未完成；释放界面事务后才完成索引更新。

**影响：** 批量恢复/永久删除可能长时间停滞，直到数据库忙等待超时；永久删除情况下，错误提示或索引状态可能与文件实际已被删除矛盾。这不是已证明永不结束的线程死锁，而是有超时的跨进程数据库锁等待。线程没有 WPF 同步上下文不能避免数据库互等。

**修复方向：** 不跨 IPC 持有界面的写事务。由服务完整执行批量操作，或先结束本地事务再请求服务；明确文件操作与索引写入失败后的恢复、核对流程。

**探针：** `Repro_BulkScope_BlocksServiceIndexWriteAfterPayloadDeletion`。

### N05 · P2 — 注册表快照超过预算后仍返回有效哈希，漏掉后续变化

**位置：** [RegistrySnapshot.cs](../../src/CleanSweep.Core/RegistryCleaning/RegistrySnapshot.cs)，第 18、46–48、114–136 行。

MaxEntries=5000。枚举超限后仅追加截断标记，仍生成可通过 Matches 的普通哈希。执行端则可能删除整个注册表子树，并不只删除已纳入快照的前 5000 项。

**复现：** 在随机 HKCU 测试键内写入 5001 个值，取得快照后修改最后一个值 v05000；前后哈希相等，Matches 返回 true。

**影响：** “执行前快照未变化”的结论对未覆盖部分不成立。另一个相邻边界是 expected 为 null 时 Matches 放行，读取失败不能天然视为已完成变化校验。这与 R05 中目标 exe 重新出现但注册表值不变的问题不同。

**修复方向：** 快照应包含完整性状态；截断、读取失败或身份不明时拒绝自动删除整树，提示缩小范围或重新确认。不要将部分内容哈希作为整树一致性的证明。

**探针：** `Repro_RegistrySnapshot_TruncationHidesChangedValue`。

### N06 · P2 — 服务没有处理的请求项，被界面当作已完成

**位置：** [ElevatedOperations.cs](../../src/CleanSweep.Core/Elevation/ElevatedOperations.cs)，第 121–134 行；[ElevationContext.cs](../../src/CleanSweep.App/Services/ElevationContext.cs)，第 99 行。

服务返回的 Incomplete 来自重新扫描后实际送入引擎的条目。请求中已经不再生成的 ID 不在其中。界面使用 `!incomplete.Contains(id)` 判断成功，没有要求该 ID 出现在显式完成集合中。

**复现：** 同一次请求包含一个有效 ID 和一个服务扫描不再生成的 ID。服务处理前者，返回 Files=1，Incomplete 不包含后者。按实际界面表达式，后者也被判定完成。

**边界：** 需要同一请求内至少还有一个实际扫描结果；所有 ID 都不存在时走另一个返回分支。探针验证真实服务响应，并核对界面判定表达式，没有启动 WPF。

**修复方向：** 为每个请求 ID 返回明确结果：完成、跳过、失败、未找到。界面只认可显式完成项，缺失结果默认未完成。

**探针：** `Repro_UnknownRequestedItem_IsAbsentFromIncompletePayload`。

### N07 · P2 — 底层权限错误被包装为 IOException，界面的服务回退条件接不住

**位置：** [HandleMove.cs](../../src/CleanSweep.Core/Cleaning/HandleMove.cs)，第 50、67 行；[QuarantineViewModel.cs](../../src/CleanSweep.App/ViewModels/QuarantineViewModel.cs)，第 70、97 行。

HandleMove 将 Win32 打开/改名失败包装成 IOException，包括 ERROR_ACCESS_DENIED。隔离区界面仅捕获 UnauthorizedAccessException 才转交服务，权限提示也只判断该类型。

**复现：** 对临时文件拒绝 Delete，对临时父目录拒绝 DeleteSubdirectoriesAndFiles，调用实际 MoveIn。抛出 IOException，HResult=5，文件保留；没有抛出 UnauthorizedAccessException。测试结束恢复原 ACL。恢复操作使用同一 HandleMove 实现，存在同样的错误传播边界。

**影响：** 某些确实需要提权的移动/恢复操作不会按设计转交在线服务，界面也可能不给出预期的权限说明。

**修复方向：** 统一返回可判定的权限错误类型或结构化原生错误码，在确认为拒绝访问时才触发服务回退；不要把所有 IOException 都当成需要提权。

**探针：** `Repro_MoveAccessDenied_IsNotTheExceptionCaughtByServiceFallback`。

### N08 · P2 — 数据更新只限制等待响应头的时间，内容读取可一直挂起

**位置：** [DataUpdater.cs](../../src/CleanSweep.Core/Integrity/DataUpdater.cs)，第 24、108–115 行；[SettingsViewModel.cs](../../src/CleanSweep.App/ViewModels/SettingsViewModel.cs)，第 357 行开始的 CheckDataUpdatesAsync。

GetAsync 使用 ResponseHeadersRead。HttpClient.Timeout 在这种模式下不覆盖后续响应体读取；ReadAsync 使用调用方 token，设置页未传入超时或可取消 token。若服务器先返回头部再停止发送正文，IsUpdating 可以一直保持为 true。

**复现：** 自定义 HttpMessageHandler 返回成功头部和停滞的内容流。HttpClient.Timeout=50ms，开始读正文 300ms 后 UpdateAsync 仍未结束；测试用调用方取消完成清理。未访问真实网络。

该超时边界与 [微软 HttpCompletionOption 文档](https://learn.microsoft.com/en-us/dotnet/api/system.net.http.httpcompletionoption?view=net-10.0) 的说明一致：ResponseHeadersRead 下需要另外限制内容读取时间。

**修复方向：** 对一次完整下载建立独立的 linked timeout token，覆盖请求头和正文读取；设置页提供取消，正确恢复状态。大小上限不能替代时间上限。

**探针：** `Repro_DataUpdate_BodyReadOutlivesHttpTimeout`。

**最终增量同类问题：** [AppUpdater.cs](../../src/CleanSweep.Core/Integrity/AppUpdater.cs) 第 86 行的程序包下载同样使用 ResponseHeadersRead，设置页 InstallAppUpdateAsync 也未传入可取消 token。程序包下载也需完整内容超时；该扩展由静态调用链确认，不重复计数。

### N09 · P2 — 安装只注册手动启动服务，没有启动或按需启动链路

**位置：** [Program.cs](../../src/CleanSweep.Service/Program.cs)，第 92–95 行；[install.ps1](../../tools/install.ps1)，服务安装分支；[CleanSweep.iss](../../installer/CleanSweep.iss)，Run；[ElevationClient.cs](../../src/CleanSweep.Core/Elevation/ElevationClient.cs)，第 28–33 行。

--install 执行 sc create，配置 start=demand，随后只写描述并返回。两个安装入口均没有启动服务。客户端探测现有管道，管道不存在则返回不可用，没有 SCM 启动请求或已配置的触发启动机制。

**结果：** 干净安装完成后服务仍停止；重启后也不会自行运行，普通权限界面无法使用刚安装的提权服务，直到管理员另外启动它。此问题会暂时遮住服务执行链中的其他缺陷，但不消除它们。

**验证：** 全链路静态确认，没有在当前机器安装、启动或停止真实服务。

**修复方向：** 明确安装后和重启后的生命周期；安装完成启动并等待 Ping 成功，同时选择适合产品的自动/触发启动或受限启动入口。启动失败须报告实际原因。

### N10 · P2 — 自定义安装目录没有传入卸载命令，卸载会删除默认目录

**位置：** [install.ps1](../../tools/install.ps1)，第 9、63 行；[uninstall.ps1](../../tools/uninstall.ps1)，第 4、26 行。

安装脚本支持 -Target，并把卸载脚本复制到该目录，但注册的 UninstallString 只指定脚本路径，未带 -Target。卸载脚本始终默认使用 ProgramFiles\\CleanSweep，最后递归删除的是这个默认目录。

**示例：** 安装到 D:\\Apps\\CleanSweep 后，从“应用和功能”卸载，执行的确是自定义目录中的脚本；但它会清理 C:\\Program Files\\CleanSweep，自定义安装文件留下。如果默认路径存在另一份安装，也会受到影响。

**验证：** 参数默认值、卸载命令和最终删除目标的静态追踪；没有运行真实安装或卸载脚本。本项针对 PowerShell 安装入口，不将此参数错误套用到 Inno Setup 自身的卸载机制。

**修复方向：** 注册卸载命令时传入实际安装根目录，或从脚本位置可靠推导；递归删除前校验规范化目标与安装标识。正确处理参数中的引号。

### N11 · P1（有前提）— 更新镜像复制沿安装目录内 Junction 删除目录外数据

**位置：** [AppUpdater.cs](../../src/CleanSweep.Core/Integrity/AppUpdater.cs)，第 206、228–260 行。

ApplyFromCurrentDirectory 只拒绝安装根本身是重解析点。CopyDirectory 递归枚举目标内所有文件，并删除源包中没有的相对路径；没有拒绝安装目录内部的 Junction，也没有固定到安装根内的真实对象。目标子目录若指向外部，枚举和删除会跟随过去。

**复现：** 临时安装目录内建一个 Junction 指向另一临时数据目录，外部目录放 user-data.txt，源目录仅有新的 CleanSweep.exe。实际 CopyDirectory 返回成功，外部 user-data.txt 被删除。未执行真实安装更新或删除用户数据。

**前提：** 安装目录中存在可跟随的目录链接，可能来自便携使用、自定义目录布局或能写该目录的主体。没有证明普通用户能在受保护的 Program Files 中任意创建链接。该缺陷独立于 R02：涉及新的程序更新镜像删除实现。

**修复方向：** 在完整目标目录树及祖先上限定操作对象，禁止跟随重解析点；依据可信安装清单删除旧版本拥有的文件，而不是删除递归枚举中所有源包缺失的文件。

**探针：** `Repro_AppUpdate_MirrorDeletesFilesOutsideInstallThroughJunction`。

### N12 · P2 — 更新没有协调运行中的服务，复制失败会留下新旧文件混合

**位置：** [AppUpdater.cs](../../src/CleanSweep.Core/Integrity/AppUpdater.cs)，第 200–253 行；[AppServices.cs](../../src/CleanSweep.App/Services/AppServices.cs)，DownloadAppUpdateAsync。

更新程序只等待旧 GUI 进程退出，随后逐文件覆盖。它没有停止或等待 CleanSweepElevation 服务，也没有建立可回滚副本/版本目录切换。某个后续目标文件占用时，重试约 5 秒后返回错误，已经替换的前面文件保留。

**复现：** 在临时安装目录锁住枚举次序较后的文件，再调用实际 CopyDirectory；返回复制失败，但第一个文件已经变成新版，锁住的文件仍是旧版。探针用普通文件模拟共享锁，没有启动真实服务。

**影响：** 在线提权服务占用可执行文件或共享程序集时存在这一触发条件；其他文件占用、权限或 I/O 故障也可触发。更新失败后程序可能无法按原版本运行，需重新安装修复。实际服务加载哪些文件及完整失败位置仍需 Windows 服务环境确认。代码内部注释已承认混合状态，但类级“失败不动现有安装”的承诺与实现不符。

**修复方向：** 安装前协调 GUI 和服务的生命周期；在受保护位置完整准备新版本，再切换版本目录或按事务式安装协议提交。失败应恢复旧版本，并按原状态重启服务，避免逐文件覆盖到一半即退出。

**探针：** `Repro_AppUpdate_LockedLaterFileLeavesEarlierFileReplaced`。

### N13 · P1（有前提）— 可写暂存目录中的程序验签后还能被替换，再被执行或复制

**位置：** [AppServices.cs](../../src/CleanSweep.App/Services/AppServices.cs)，第 224–239 行；[AppUpdater.cs](../../src/CleanSweep.Core/Integrity/AppUpdater.cs)，第 118–145、176–184、200–242 行。

下载完成会校验发布信息签名、包大小和 SHA-256；这些检查是有效的。但解压后的目录没有绑定不可变的内容清单或收紧到独立可信主体。LaunchApply 从该暂存目录执行 CleanSweep.exe，安装目录不可写时使用 runas；第二阶段直接将自己的目录复制到安装目录，没有再次依据签名发布包核验待执行/复制内容。

**复现：** 用临时密钥生成有效的发布元数据和三个已签名数据集，核对包哈希并让 Stage 成功；然后把暂存 CleanSweep.exe 的内容替换为另一段测试文本。实际 CopyDirectory 仍返回成功，安装目标收到替换后的内容。没有执行这个测试 exe，也没有请求 UAC 或写入真实安装目录。

**前提与边界：** 需要另一个进程能够写暂存目录，并在验证后、执行/复制前替换内容。普通权限界面的 LocalAppData 分支属于当前用户可写；共享数据目录分支的实际可写主体取决于 ACL。这里证明签名信任未延续到最终安装内容；不等于签名算法被破解，也不等于已证明绕过 UAC。若用户接受原有更新流程的提权提示，运行对象必须仍是被验证的那一个。

**修复方向：** 使用受信任、不可被当前普通进程替换的更新执行器。由它在受保护目录独立验证签名发布包、解压、固定对象身份并安装；不要先从攻击者可能写入的暂存区执行一个声称能自证可信的程序。验证后仅再按可变路径重读仍有竞态。

**探针：** `Repro_AppUpdate_StagedExecutableCanChangeAfterVerification`。

## 五、验证边界与建议顺序

### 验证边界

- 文件、数据库、硬链接和 Junction 复现限定在独立测试目录。ACL 探针只修改临时文件及其父目录，并恢复原 ACL。
- 注册表写入限定在随机 HKCU 测试分支，结束后删除测试键。没有删除系统受保护键。
- 超时测试仅运行访问 127.0.0.1 的 ping；HTTP 停滞由进程内模拟流产生。
- 未安装/启停真实系统服务、创建/删除真实计划任务、删除驱动、填满磁盘、清理系统内存或运行 SFC/DISM。
- 未完成 WPF 自动化、不同 Windows 版本、ARM64、多账户 SYSTEM 服务端到端、断电恢复或长时间竞态压力测试。
- N02 的两库冲突、N04 的两连接锁等待、N07 的底层异常类型均已实际验证；由此到完整 UI/权限场景的连接关系来自静态调用链。报告没有把组件复现等同于完整攻击链。

### 建议修复顺序

1. **先约束实际删除/移动与程序执行对象。** 修复 R01、R02、R08、N11 的直接数据损失边界，以及 N01 的确认快照、N02 的隔离对象身份、R07 的对象授权、N13 的更新暂存信任。
